## วิธีออกเคส

1. **อ่านระบบจริงก่อนเขียนเคส** — BR + design file เป็นหลัก แต่ถ้าสงสัยให้ไปดูโค้ด
   เคสที่เขียนจากสมมติฐานคือหนี้ที่ต้องมาใช้คืนทีหลัง
2. **ครอบคลุมเส้นทางที่ผู้ใช้เจอจริง** ไม่ใช่แค่ happy path —
   ข้อความ error ทุกเคสต้องตรงตัวอักษรกับที่สเปกกำหนด (`code` ของ error frontend พึ่งพาอยู่)
3. **หาเคสที่ "ผ่านตาง่าย"** — กฎที่มีหลายเงื่อนไขแต่โค้ดเช็คไม่ครบ, ปุ่มที่กดซ้ำเร็ว ๆ,
   การถอยกลับไปแก้ข้อมูลแล้วเดินหน้าใหม่, ข้อมูลที่ค้างจากการกรอกครั้งก่อน
4. **แยกให้ออกระหว่าง "ทดสอบแล้วผ่าน" กับ "ทดสอบไม่ได้"** —
   ข้อจำกัดของ environment ทำให้บางเคสรันไม่ได้ ต้องเขียนว่า **ยังไม่ได้ทดสอบ**
   ไม่ใช่ทำเครื่องหมายผ่าน แล้วระบุว่าต้องไปทดสอบที่ env ไหน

## 🔴 กับดัก: "เขียวแล้ว" ที่แปลว่ายังไม่ได้ทดสอบอะไรเลย

- **ชุด test ที่สำคัญที่สุดอาจไม่ผูกกับ build หลัก** — ถามให้ได้ว่า requirement นี้ชุดไหนคุม รันด้วยคำสั่งอะไร
  (บันทึกโปรเจกต์มี) · build เขียวไม่ได้แปลว่าชุดนั้นถูกรัน
- **test task ที่หา test ไม่เจอ** (ไฟล์ถูก gitignore · filter ผิด) build tool หลายตัวตอบ success ทันทีโดยไม่เตือน
  ⇒ **เชื่อผลเขียวเฉพาะรอบที่พิมพ์ชื่อ/จำนวน test ออกมา** · เขียวเร็วผิดปกติ = **ยังไม่ได้ทดสอบ**
  ต้องเข้ากอง "ทดสอบไม่ได้" ไม่ใช่กอง "ผ่าน"
- **test เขียวครบ ≠ requirement ครบ** — เช็คว่ามี requirement ไหนที่ไม่มี test คุมเลย หรือ assertion
  ที่เป็นโมฆะไปแล้วเพราะรูป response เปลี่ยน · ข้อไหนไม่มีอะไรคุม **ต้องมีเคสของเราเอง**
- **บอกให้ชัดว่าทดสอบได้ถึงชั้นไหน** — "ยิงออกจากเซิร์ฟเวอร์เราได้" ≠ "ผู้ใช้ได้รับจริง"

## เวลาโดนถามว่า "พร้อมส่ง UAT ไหม"

ตอบเป็นสามกอง ไม่ใช่คำเดียว:

- **ทดสอบแล้วผ่าน** — เคสไหนบ้าง
- **ทดสอบแล้วไม่ผ่าน** — defect พร้อมขั้นตอนทำซ้ำ
- **ยังทดสอบไม่ได้** — เพราะอะไร ต้องการอะไรถึงจะทดสอบได้

ถ้ากองที่สามไม่ว่าง **ยังไม่พร้อมส่ง UAT** ต่อให้กองแรกจะยาวแค่ไหน — พูดออกมาตรง ๆ
อย่าให้คนอ่านต้องเดาเอง
